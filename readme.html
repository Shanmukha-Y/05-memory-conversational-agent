memagent — a conversational agent that remembers across restarts

Two-tier memory: a token-budgeted rolling buffer for the live conversation, and a persistent vector store of distilled facts that survives the process dying. Kill it mid-conversation, restart it, and it still knows your name, your project, and what you decided last session.

Python 3.11+ uv ChromaDB (local, persistent) SQLite qwen3.5:9b via Ollama nomic-embed-text via Ollama pydantic · rich

Why naive chat history fails

The obvious way to give a chatbot memory is: keep appending every turn to the prompt. That fails in two directions at once, and they're the same failure wearing different hats.

  • Context growth. A prompt that grows by every turn eventually blows the context window, and long before that it blows the latency and cost budget — you're re-sending the entire conversation, including the parts that stopped mattering an hour ago, on every single call.
  • Forgetting. The standard fix — a sliding window that only keeps the last N turns — solves the growth problem by deleting the memory problem. Once a turn scrolls out of the window it's gone. Ask the agent your name after turn 40 and it has no idea, even though you told it at turn 2.

Both failure modes come from treating "what's in the prompt" as the only kind of memory the agent has. It's not: there's a difference between what you need verbatim, right now (the live back-and-forth) and what you need as a fact, indefinitely (your name, your project, a decision you made). Conflating them means paying full verbatim-storage cost for durable facts, and losing durable facts the moment verbatim storage gets pruned.

The rolling buffer never grows past budget

Every turn goes into the buffer verbatim. Token cost is estimated cheaply (chars/4 — a real tokenizer would be more precise but this is only used to decide "is it time to compress," where a rough estimate is fine). Once the buffer reaches 80% of its budget, the oldest half is summarized into a single turn marked [compressed], and the last keep_last_n_turns turns stay verbatim. Compression triggers at 80% rather than 100% deliberately: it leaves headroom so the next prompt — which still includes the pre-compression buffer for one more turn — never blows past budget either.

Nothing said is ever actually deleted. The raw turns being compressed are already sitting in the SQLite transcript log (written before compression ever runs), and every compression + extraction event is logged to an audit table. Compression only shrinks what rides along in the prompt, never the historical record.

Fact extraction: only what's durable

Whatever gets compressed out of the buffer is handed to the same model in JSON mode, prompted to pull out only facts that matter beyond this conversation — identity, preference, project, or decision — and to return an empty list for pure chit-chat. Output is validated against a Pydantic schema with one retry on malformed JSON.

Scored recall: why pure similarity fails

Naively, "what does the agent know about this user relevant to what they just said" is a nearest-neighbor search over embedded facts. That's not enough on its own: pure similarity ranking lets a fact that happens to be semantically close to the current question outrank a fresher, more relevant one, even if it's months stale or was later superseded. The score blends three signals multiplicatively, so any one of them collapsing to near-zero kills the memory's relevance:

score = similarity × e^(-age_days / half_life_days) × (importance / 5)

Half-life defaults to 30 days. A fact's "age" is its updated_at timestamp, not created_at — so a fact that gets reaffirmed or corrected gets a fresh recency boost, which is what makes contradiction handling (below) actually improve future recall instead of just fixing the stored text. The top-4 highest-scoring facts get formatted into a "Known about this user:" block and injected into the system prompt for that turn — and only that turn; nothing is permanently baked into the buffer.

The scoring formula is a pure function with no I/O (recall.score_memory), so its ordering guarantees — a fresh important fact beats an old merely-similar one — are covered by exact-ordering unit tests, not just eyeballed.

Contradiction handling

Every newly extracted fact is embedded and compared against the user's existing facts before being stored. If the closest existing fact is above a similarity threshold, the pair is handed to the LLM to decide replace, merge, or skip — rather than blindly inserting a new row and letting near-duplicate or contradictory facts accumulate as garbage.

The threshold isn't 0.9, and that's a deliberate, measured choice. The plausible-looking default — "cosine similarity above 0.9 means duplicate" — turns out to be wrong for this use case. Measured against nomic-embed-text:

PairCosine similarity
"User is building a RAG system" / "The user works on a RAG system" (paraphrase)0.906
"User lives in NYC" / "User moved to Boston" (contradiction)0.714
"User uses Chroma as their vector database" / "User switched from Chroma to Qdrant" (contradiction)0.791
"User lives in NYC" / "User prefers dark mode UIs" (unrelated)0.391

Genuine contradictions about the same "slot" — the exact cases this gate exists to catch — score lower than intuition suggests, well below a 0.9 bar. A 0.9 threshold would have let every contradiction case sail through as a fresh insert, silently duplicating instead of updating. dedup_similarity_threshold is set to 0.65: comfortable margin above the unrelated ceiling (~0.44) and below the lowest observed contradiction score (~0.71).

When the LLM says replace, the existing SQLite row is overwritten in place — same UUID, same row, new text, new embedding, bumped updated_at — and the old text is written to the audit log for transparency. Nothing is duplicated. /memories after "I switched from Chroma to Qdrant" shows one updated fact, not two conflicting ones.

The /why transparency command

Every recall is inspectable. /why shows exactly which memories were pulled for the last reply and their full score breakdown — similarity, age in days, decay factor, importance, and the final score — so nothing about "what does the agent think it knows" is a black box.

A second finding: the assistant's own small talk can contaminate memory

During live verification, a stored fact read: "User plans to use controlled rollout to gather ground truth for evaluation metrics like Recall@K or MRR." Nobody ever said "Recall@K" or "MRR" anywhere in that conversation. Tracing it through the audit log and raw transcript to the exact source turned up something more specific — and more interesting — than generic hallucination.

The extractor's turn filter originally read t.role in ("user", "assistant") — it treated the assistant's own conversational replies as legitimate source material for "facts about the user." And a chat model, replying naturally to "I'm building a RAG system for our internal knowledge base," doesn't just acknowledge it — it elaborates: "That sounds like a high-impact project, especially for getting operational docs and SOPs into the pipeline." Nobody said "operational docs and SOPs" either; the assistant added it as friendly color commentary, the same way a person might say "oh nice, so like for onboarding docs?" without that being a claim about anything. That's completely normal chat behavior. The bug was extracting facts from it anyway.

Traced, not guessed. Querying the live run's audit log and transcript table side by side showed the chain precisely:

  1. Real turn: "I'm building a RAG system for our internal knowledge base."
  2. Assistant's reply invents: "...getting operational docs and SOPs into the pipeline."
  3. Next compression's summary, given both turns as equally-valid input, elaborates further: "...defining chunking strategies... selecting an embedding model such as text-embedding-3-large..." — a specific, real embedding model name that never came up, invented from nothing.
  4. A later summary escalates again: "...evaluation metrics like Recall@K and MRR."
  5. Extraction, reading the (real, un-summarized) turns from that window, independently reached the same territory and stored it as fact.

Each stage treats the previous stage's output as established truth and elaborates on top of it — a small, compounding game of telephone, entirely internal to the model.

Fix: extractor.py now sources facts exclusively from the user's own turns (t.role == "user") — never the assistant's replies, and never summary turns (which were already excluded, but that filter alone didn't touch this bug, since the contamination came from live assistant chat, not summarized text). The extraction and summarization system prompts were also both tightened to explicitly forbid adding plausible-sounding details, tools, or terminology that weren't actually said, as defense in depth. A dedicated test (test_extract_facts_never_sends_assistant_content_to_the_model) plants a fabricated specific in an assistant turn and asserts it never even reaches the extraction prompt, not just that it's absent from the output.

Residual limitation: the short-term buffer's [compressed] summaries (used only for conversational continuity within a session, never for long-term storage) can still drift over many re-compression cycles, since the summarizer sees both roles by design — that's necessary for it to track what the assistant already told the user. The blast radius is now bounded to that single session's live context window rather than permanent memory, and re-tuning the buffer budget so compression doesn't fire on nearly every turn (see below) independently reduces how many re-summarization cycles a session accumulates in the first place.

Design talking points

  • Two-tier memory with honest token budgets. The prompt assembled for turn 200 is roughly the same size as the prompt for turn 5: a bounded buffer plus at most 4 recalled facts. The agent never forgets a durable fact, and the bill never grows unbounded either.
  • Recency decay is load-bearing, not decorative. Without it, a stale-but-similar fact from months ago can outrank something said five minutes ago. The exact-ordering unit tests in test_recall_scoring.py exist specifically to keep this property honest as the formula evolves.
  • Contradiction handling is memory that updates, not memory that accumulates. The dedup threshold was set from measured embedding behavior, not intuition — see the calibration table above. That 0.9-vs-0.65 gap is the difference between a demo that silently fails on its own money-shot scenario and one that doesn't.
  • /why makes every recall inspectable. "Trust the agent's memory" is a much easier sell when you can see the similarity, the recency decay, and the importance behind every fact it surfaced.
  • Nothing is silently destroyed. Compression shrinks what rides in the prompt; the SQLite transcript keeps the verbatim history; the audit log keeps a record of every compression and every dedup decision (replace/merge/skip), including what the superseded text used to say.

Stretch goals (not implemented)

  • Memory consolidation pass — a nightly job that merges related facts, closer to how sleep consolidates memory.
  • Episodic vs. semantic memory split — events ("we shipped v1 on the 12th") vs. facts ("uses Qdrant") as distinct stores with different recall behavior.
  • Shared-memory mode — two agent instances, one user, consistent memory with sync conflict handling.
